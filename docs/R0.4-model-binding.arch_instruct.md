# R0.4 — Model Binding (amends CORE §8)

**Class:** arch_instruct · **Pass:** R0 · **Status:** issued
**Depends on:** R0.1
**Touches:** `docs/PSYKI_CORE.md` §8, `roles/agentagent/config/agent.config.json`

---

## 1. Decision

CORE §8's candidate table is replaced. VibeThinker-3B is withdrawn as a runtime
binding and retained as a **design concept for a future fine-tune**, not a
dependency. The live roster is Claude, Gemini, Gemma, Phi.

| Role | Binding | Rationale |
|---|---|---|
| **AgentAgent** | Claude (largest available) | heaviest role; design and test authoring gate everything downstream. Anthropic account is the primary spend. |
| **Emissary** | Gemma | multimodal, conversational; the membrane is a disambiguation dialogue, and it must handle images and mixed input as first-class. Also the primary interpreter of returned data. |
| **PSY** | Phi | small, strong single-shot logic, no dialogue, no tools. Runs on the local box. Matches PSY's actual shape: it reads a sealed context once and emits a plan. |
| **TaskMaster** | Gemini | model-binding and capability-floor decisions are cheap reasoning over a config space; Google account covers this for the next year. |
| **Escalation tier** | Claude | tier-2/3 escalation when a contract exhausts retries on genuinely hard work (CORE §6). |
| — | ~~VibeThinker-3B~~ | withdrawn: licensing is not compatible with the other bindings. Preserved as a target architecture if PSYKI ever trains its own PSY. |

**Copilot is explicitly out of scope for any automated role.** It holds no
position in the binding table and no credential in this system.

---

## 2. Consequences

**Local vs remote splits the system in two.** Phi (PSY) runs locally; Claude,
Gemini and Gemma run behind APIs. CORE §8 says *"residency is a schedule, not an
allocation"* and that model swap cost is unmeasured — but with a mixed local/API
roster, "swap cost" is not one number. It is at least three:

1. local model load/unload (GPU-bound, seconds)
2. API round-trip latency (network-bound, sub-second, but rate-limited)
3. **quota exhaustion** (bound by billing, and it is a *hard stop*, not a slowdown)

Item 3 does not appear anywhere in CORE and is the one that will actually bite.
A closed loop with no human in it (CORE §6) that exhausts an API quota mid-cycle
has no defined behaviour. `HomeostaticBudget` from v0 is the natural home for
this — it becomes a real, externally-grounded constraint rather than a
biologically-motivated one, which is a strong argument for its survival under the
ablation rule. **FLAG-11.**

**The capability floor is now heterogeneous.** CORE §4.2's `capability_floor`
(context, modality, tool-calling) has to express "must be multimodal" for
Emissary-adjacent contracts and "must run locally" for anything under a data
residency constraint. The field as specified cannot express residency. **FLAG-12.**

**Gemma as both Emissary and data interpreter is a concentration risk.** Every
untrusted byte in the system crosses one model. If Gemma's tool-calling or
structured-output reliability is weaker than Gemini's on this workload, I13
(encode verification, R0.2 §5) is not optional — it is the only thing standing
between a lossy encode and a silently wrong plan. Measure before committing.

---

## 3. What must be measured before R3 closes

CORE §8 says to measure swap cost early. Concretely:

| Measurement | Why it gates |
|---|---|
| Phi load→first-token on the local box, cold and warm | determines whether a PSY cycle is seconds or minutes |
| Gemma enum-encode accuracy on a held-out intent set | directly determines I13's necessity and threshold |
| Claude tokens per authored contract, p50/p95 | determines burn rate, and therefore how long the loop can run unattended |
| Gemini quota headroom per day under the Google account | the hard stop in §2 item 3 |

None of these are expensive to run and all four are currently unknown numbers
that the latency and cost picture depends on entirely.

## 4. Flaw enumeration

- **Model identifiers are unverified.** Exact model IDs and availability post-date reliable knowledge here and must be confirmed against current provider docs at bind time. CORE already treats model IDs as deploy-time policy, so this is contained — but the *capability assumptions* above (Gemma multimodal, Phi strong-logic-small) should be re-checked, not inherited from this document.
- **Free-tier and promotional accounts are not infrastructure.** The Google account is a one-year grant. A system designed around it acquires a cliff at month twelve. Vendor-agnosticism is the stated architectural constraint precisely to survive this, and it only holds if the adapter layer is real — which it is not yet.
- **Four vendors is four adapter surfaces, four auth flows, four failure modes, and four sets of rate limits,** for a system that currently has zero adapters and no CI. The roster is correct for capability and cost; it is aggressive for the current state of the tree.
- **Role→model is asserted here without measurement.** Phi-as-PSY in particular is a bet that planning-over-sealed-context is within a small model's reach. If it is not, PSY escalates to Gemini and the local-first property is lost. That should be tested with a real sealed context in R3 before anything is built on top of it.

## 5. Open flags

- **FLAG-10** — confirm current model IDs and availability against provider documentation at bind time. Owner: R3.
- **FLAG-11** — API quota exhaustion has no defined behaviour in a loop with no human. Assign to `HomeostaticBudget`. Owner: R3.
- **FLAG-12** — `capability_floor` cannot express residency (local vs API). Extend the field in R2.3. Owner: R2.3.
- **FLAG-13** — no adapter layer exists. Vendor-agnosticism is currently a stated principle with no implementation. Owner: R3.
